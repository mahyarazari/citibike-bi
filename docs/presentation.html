The business problem

Empty and full stations lose rides

A rider who finds no bike, or no free dock, is a lost trip and an unhappy customer. The report supports four decisions:

1 · Rebalancing

Which stations are empty or full now, and which will run out soon → a truck dispatch list.

2 · Demand planning

When and where demand peaks: hour × weekday × station.

3 · Customer growth

Casual riders who ride like commuters → membership campaign.

4 · Network expansion

Busiest routes, overloaded docks, under-served neighborhoods.

Design rule: every chart shows context (trend or per-capita rate), a benchmark (city average or target) and a one-line → action.

Architecture

From API to action, fully automated

1. Extract

  • GBFS discovery → live feeds
  • S3 listing → newest month
  • Resumable downloads with retries
  • Manifest = incremental load
→

2. Clean & model

  • Python · polars · DuckDB
  • 11 trip rules + 7 station rules
  • pandera schemas, 31 tests
  • Star schema, Parquet < 50 MB
→

3. Automate

  • GitHub Actions
  • Live job every 30 min
  • Trip job on the 5th
  • Outputs on the data branch
→

4. Report

  • Power BI project (TMDL + PBIR)
  • Reads public raw URLs
  • No gateway needed
  • Generated from code

The BaseUrl parameter switches the whole report to another data source in one place. Parquet is read first, with CSV as a fallback.

Fair comparisons

Rates, not raw totals

A big neighborhood or station must not look better just because it is big. Rankings use:

Per 1,000 residents

Trips, bikes and docks per 1k people (2020 Census). Parks and airports have no population → shown as blank, never divided by zero.

Per dock

Trips per dock per day shows real pressure on a station, independent of its size.

Index vs city = 100

Every map metric becomes an index, so one diverging colour scale works for all of them.

Week over week

With one month of trips, trends compare the last 7 days with the 7 before.

Same-hour baseline

Weather impact compares each hour with the normal level for that hour, removing time-of-day bias.

Targets

Balanced ≥ 85% · empty or full ≤ 5% · data age ≤ 60 min · rows removed ≤ 1%.

How targets are estimated

The open data has no rider id. A casual rider repeating the same origin → destination at least 3 times in one week, on weekday commute hours and under 30 minutes, counts as one likely commuter. This is a conservative lower bound. Price ($220 default) and conversion rate (10% default) are adjustable what-if parameters.

→ Start the campaign at the station with the most repeat casual commute trips

Key findings · October 2026 + live snapshot

What the data says

Supply

About 15% of stations were empty or full at the snapshot (222 empty, 127 full), well above a 5% target; 69% balanced vs 85% target.

Demand

5.08M trips in October (≈164K/day). Strong weekday commute peaks; rain cuts trips by about two thirds.

Customers

82% of trips are by members and 74% on e-bikes. ≈2,430 casual riders per week behave like commuters.

Data

Only 0.10% of trips removed; 6 retired station ids explain 26.7K trips and are kept, not lost.

Recommended actions · limitations

What to do next

Prioritised actions

  1. Run trucks from the dispatch list, starting with the highest-priority station.
  2. Pre-position bikes in morning-draining neighborhoods before 7 AM.
  3. Launch a membership offer at stations with repeat casual commuters.
  4. Add docks at stations above 1.5× city utilization.
  5. Plan new stations in dense, under-docked neighborhoods.

Limitations

  • One month of trips (download speed) → week-over-week instead of month or year trends.
  • Population from the 2020 Census.
  • No rider id → conversion targets are estimates.
  • Live history builds up from the first run (14-day window).
  • GitHub cron can start a few minutes late.
